## 六、"能不能用这个源码编译得到这个 APK？"

- **功能上：能。** 编译公开源码得到的是 4.6.10（versionCode 558），与你手里的 4.6.11 在代码功能上完全同源，只差上面 3 处小改动。若想手工补齐：改版本号为 4.6.11/559，替换上述两个 hook 类名字符串，再在某处加上"阿巴阿巴阿巴~~"即可得到功能等价物（该字符串的准确位置无法从公开信息推断）。
- **字节上：不能完全一致。** 作者签名私钥不可能获得（自签证书指纹必然不同）；R8 的 `pg-map-id` 每次构建不同；资源短文件名（res/2j.xml 等）与构建时间戳也不一致；项目未配置 reproducible builds。这是所有第三方编译的必然结果，不影响安装使用。
- 注意：自编译版与本机自签名后**与作者签名不兼容**——不能覆盖安装官方版（需先卸载，会丢模块配置）。

## 九、libxposed 新 API（102）迁移说明

应用户要求，将模块从传统 Xposed API（`de.robv.android.xposed`，api-82 jar）整体迁移到 **`io.github.libxposed:api:102.0.0`**（Maven Central 上的新式 Xposed API，AAR 发布），并重新编译。

**入口与声明方式的变化**：

| 旧（api-82） | 新（libxposed 102） |
|---|---|
| `assets/xposed_init` 声明 `IXposedHookLoadPackage` 实现类 | `META-INF/xposed/java_init.list` 声明 `XposedModule` 子类（已删除 xposed_init） |
| `xposedscope` manifest meta-data | `META-INF/xposed/scope.list`（内容与原 @array/scope 一致，meta-data 保留无害） |
| 无对应机制 | `META-INF/xposed/module.prop`：minApiVersion=101、targetApiVersion=102、exceptionMode=protective、staticScope=true |
| `handleLoadPackage(lpparam)` | `onPackageLoaded(PackageLoadedParam)` |
| `handleInitPackageResources(resparam)` | 新 API 无资源回调，见下文兼容方案 |
| `initZygote` | 新 API（101 起）不再注入 zygote，各模块该方法保留但不再被调用 |

**兼容层设计**（`com.coderstory.flyme10.xposedcompat`，13 个 Java 文件）：为了把 7 个功能模块的改动压到只换 import，兼容层用 **Java** 复刻了旧 API 的全部签名（`XC_MethodHook`/`XC_MethodReplacement`/`MethodHookParam`/`XposedBridge`/`XposedHelpers`/`LoadPackageParam`/`InitPackageResourcesParam`/`StartupParam`/`XSharedPreferences`/`AndroidAppHelper`），内部全部用新 API 实现：

- hook 桥接（`HookerImpl`）：旧 before/proceed/after 模型 → 新拦截器链。语义映射与旧 XposedBridge 一致：before 中 `setResult/setThrowable` 跳过原方法、after 钩子始终执行、before 改参数透传原方法、回调异常捕获并记日志（module.prop 同时声明 protective 模式兜底）。
- `findAndHookMethod/findAndHookConstructor/hookAllMethods/hookAllConstructors`：反射解析 `Member` 后调 `hook(Executable).intercept(...)`；方法查找支持继承链（顺带修复了旧版可能 hook 不到父类方法的边角情况）。
- `XposedHelpers.getObjectField/setObjectField/setBooleanField/getIntField/callMethod`：纯 Java 反射重实现，无任何旧框架运行时依赖。
- 偏好读取：`XSharedPreferences` 兼容类直接解析模块 App 的 `shared_prefs/UserSettings.xml`（与旧实现同一数据源，含 /data/data、/data/user/0、/data/user_de/0 三路径自动回退与 mtime 变更自动重载），UI 端零改动。
- 资源替换（新 API 无资源回调）：`XResCompat` 按旧 `XResources.setReplacement` 的两种签名（int id / pkg+type+name）入队，模块加载时 hook `ContextWrapper.attachBaseContext`，在宿主 App 的 Resources 就绪后通过宿主框架的旧版 XResources 桥反射生效（LSPosed 在每个作用域进程都提供该桥）；框架不提供时优雅降级为跳过并记日志，全部方法 hook 不受影响。

**7 个功能模块**（IsEnable/HideApp/Others/ThemePatcher/FuckAd/SystemUi/Start）与 `IModule`、`XposedHelper`、`Log` 基本只改了 import；`KotlinXposedHelper.kt`（456 行旧 DSL 死代码）精简为仅保留 `SystemUi` 用到的 `getObjectField` 扩展。

**运行环境要求**：需要**支持 libxposed 新 API 的框架**（较新版本的 LSPosed / 未来实现 API 101+ 的框架）才能加载；仅在旧框架上使用时请继续使用此前的传统 API 版本 APK。由于 minApiVersion=101（不使用热重载等 102 专有特性），兼容所有已实现 101 的框架。

**已移除的旧激活检测（修订）**：原 MainActivity 有两处"模块未激活"门禁，在 libxposed 版上必然误报，已删除——
1. `checkEnable()`：App 内 `isEnable` 硬编码 false，原设计靠旧框架把模块注入自身 App 进程、由 `IsEnable` 模块 hook 该 getter 改为 true；新 API 严格按 scope.list 注入（模块自身不在作用域），hook 永远不生效，于是每次启动都弹"检测到插件尚未在框架中激活"。
2. `checkDialog()`：用 `getSharedPreferences("test", MODE_WORLD_READABLE)` 是否抛 `SecurityException` 判断激活状态，误报时弹"插件配置初始化失败"并在确定后**强制杀进程**。

两处文案在最终 APK 的 dex 与资源中均零残留（shrinkResources 连未引用的对话框布局一并清除）。模块实际是否激活，以 LSPosed 管理器中的勾选状态为准。

**真机日志排查（LSPosed 2.2.1，2026-10-18）——所有 hook 失效的根因与修复**：

用户反馈"模块已加载但所有 hook 项失效"。日志（modules/verbose）证据：
1. 模块在每个作用域进程正常加载并 dispatch（`Flyme助手已加载（libxposed API 102，框架 LSPosed 2.2.1）`）；
2. hook 桥端到端工作正常——`attachBaseContext` 的 hook 实际触发、回调打出日志；
3. 但现代版运行时段**只有无开关条件的 hook 留下痕迹**（systemui 两个类缺失报错、launcher 的 load config、weather 的两个 CNFE——全部在纯包名判断块里），所有带 prefs 开关的 hook 一个都没注册；
4. 传统版时代日志中出现 `New modules detected, hook preferences`（框架在模块 App 内 hook 偏好并放开文件可读性），现代版时代从未出现。

根因：兼容层最初用**直读文件**方式读 `UserSettings.xml`。传统框架会把模块配置文件放开为全局可读（xposedsharedprefs 机制），但 **LSPosed 2.x 现代加载路径不做这件事**——文件 0600、属主是模块 uid，宿主进程必然读不到 → 所有开关读到默认 false → 所有功能 hook 不注册 → "全部失效"。

修复（v3）：`XSharedPreferences` 兼容层改为**优先使用 API 101+ 的正规机制 `getRemotePreferences(group)`**——框架的特权服务把模块 App 的 shared_prefs 分发给各作用域进程（模块 App 端写入逻辑零改动），单次调用失败或嵌入框架时回退文件直读。同时在 `onModuleLoaded` 增加每进程一条诊断日志：`偏好读取: 框架远程服务/配置文件直读，N 项配置`——今后一眼可判配置是否读到。

同时确认为**预期限制**（非缺陷）：LSPosed 2.x 现代模块路径不提供旧版 XResources 桥，资源替换类功能（主题试穿文案"开始白嫖"的字符串替换、customizecenter 的"阿巴阿巴"日期头样式）在 `attachBaseContext` 回调中探测失败后按设计优雅降级为跳过并记一次日志；方法类 hook 功能不受影响。

**v3 真机验证结果与 v4 迭代（资源模拟替换）**：

v3 上机：远程偏好服务连通（`偏好读取: 框架远程服务`诊断日志出现于每个作用域进程），"显秒"生效——证明 getRemotePreferences 修复方向正确。用户卸载重装后配置尚未写回时进程加载，诊断显示 `0 项配置`，属时序问题：卸载重装清空了数据，加载先于配置写入；时钟 hook 每次刷新重读配置所以自动恢复，但**加载时读配置的功能**（含电量%）在该次进程生命周期内都拿不到开关。⇒ v4 将兼容层改为：远程快照为空时回退合并文件直读，且**改完配置后需重启作用域应用**（现代路径下框架不会注入模块自身 App、无法监听配置变更自动重启作用域——传统路径的"hook preferences"机制依赖注入）。

电量加%失效的另一半原因：它替换的是 systemui 包内字符串 `status_bar_settings_battery_meter_format_simple`（格式 `%d%%`），属**资源替换**。经查证：LSPosed 官方 Wiki 明确"Resource hooks are removed"（现代 API 已移除资源 hook，恢复方式未定）；社区方案 EzHookTool（lingqiqi5211，提供 hook-xposed-101 变体）与 HyperCeiler 的 ResourcesTool 采用**拦截 Resources/TypedArray getter、按包名+类型+名称匹配替换**的模拟技术。v4 未引入 RC 状态的第三方依赖，而是在 ResourceCompat 兼容层内嵌同款技术：旧桥缺失时 hook `Resources.getString(int)`/`getText(int)`/`getString(int, Object[])`，按运行时解析出的资源 ID 匹配替换值（名称式替换用 getIdentifier 解析，ID 式直接使用）。覆盖 Java 代码层的资源取值（电量格式即此类）；XML 布局/样式原生解析路径无法拦截，"阿巴阿巴"（style 替换）仍按设计跳过并记日志。

**v3/v4 真机结论与 v5 重构（配置通道）**：

v4 与降级回 v3 的运行日志均显示 `偏好读取: 0 项配置（远程服务=true）`——**LSPosed 2.2.1 的远程偏好服务实际上从未送达过用户配置**。此前 v3 上"显秒"一度生效，属框架服务的延迟同步的偶然产物；反复安装切换后彻底断供。根因：远程偏好的数据供给依赖"把模块注入其自身 App 进程并 hook 其偏好写入"（日志中 `hook preferences` 事件，仅传统路径存在）或模块 App 侧集成 libxposed:service 库——现代路径两者皆无。

**v5 方案：绕开框架，启用原作者预留的跨进程通道**。App 本就声明了导出的 `com.coderstory.flyme10.PreferencesProvider`（SharedHelper 读写全走它）：
1. 给 Provider 增加 `call("getAll", spName)` 全量读取接口（Bundle 返回，5 种类型）；
2. 兼容层 `XSharedPreferences` 在远程快照为空时改为查询该 Provider（进程级共享 1 秒 TTL 缓存，避免时钟每秒多次 IPC）——宿主进程跨进程拉取 App 端文件的**实时**内容，不再依赖框架同步；为此加载期（宿主 Application 尚未创建）通过 ActivityThread 系统上下文获得 ContentResolver；
3. 电量百分比替换改为**注册时无条件、查询时判开关**（Replacement 携带 gateKey，模拟层每次命中时经同一通道读 `show_icon_battery_percentage`）：开关切换即时生效、无需重启 systemui、重启手机不失效；
4. proguard 增加两个 Provider 类的 keep 规则。

**v6 真机定位与最终修复（DE 存储 + Direct Boot）**：

v5 日志（2026-10-19）出现决定性证据：`com.meizu.flyme.update`（uid 1000）在进程启动 19ms 内经 **provider 通道拿到全部 13 项配置**，而同一时间窗内重启的 systemui、launcher、customizecenter（普通 uid）全部 0 项。结论：通道本身可用，但 Android 对**安装后未再打开过的 App（stopped 状态）**，普通 uid 进程的 provider 调用会被系统拦截（uid 1000 系统进程豁免）——这解释了历次日志"通道连通却总是 0 项"的分裂现象。

v6 修复（同时覆盖"重启后第一次解锁不生效"）：
1. **配置存储整体切换到设备加密存储（DE，/data/user_de）**：`Utils.getMySharedPreferences` 改经 `createDeviceProtectedStorageContext()`，App 端全部读写（provider、设置界面、SharedHelper）一处切换全量生效；旧 CE 配置在 App 启动时一次性迁移（仅 DE 为空时执行，不回滚新配置）。
2. **provider 标记 `directBootAware="true"`**：解锁前（Direct Boot）systemui 拉起 provider 即读到 DE 配置。hook 的注册时机本就在 systemui 代码运行之前（历次日志可证），此前缺的只是这一刻配置不可读——DE + directBootAware 补齐最后一环；`Application` 在 DE 模式下跳过友盟初始化保证 provider 稳定。
3. 探针升级为逐通道计数（`provider=P 远程=R 文件=F`，-1 为通道异常），日志可直接判定通道健康度；兼容层 `getAll()` 改为 provider 优先。
4. 按用户要求**移除主题无限试用**（模块、开关、文案全部删除，避免与 FlymeTool 冲突），保留去广告等其余功能。

使用要点：**每次安装/升级后必须打开一次 App**（解除 stopped 状态并触发 CE→DE 迁移）。
